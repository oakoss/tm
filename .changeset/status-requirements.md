A Scheme file's Workflow Status can list the fields it `requires`, such as `{ id = "doing", category = "active", requires = ["area"] }`. An Issue cannot enter that Status, be created in it, or clear one of those fields while there: the write is refused with `missing_fields` naming the `target` Status, and `tm create`, `tm move` and `tm start` add each field's allowed values and a fix that gives them. A requirement binds only types that carry the field, and requiring `priority` means a priority other than `none`. An Issue short of its first active Status's fields stays in `tm ready`; `tm start` refuses it with the edit that gives them, and `tm next` passes it over, naming that edit when nothing else can be taken. Since `tm start` assigns the Issue, requiring an assignee does not stop a start. A parent following its child, or an Issue `tm git scan` closes, is left where it is with a warning; `tm git scan --dry-run` reports the same, and a later scan retries. `tm undo` and imports are not held to these requirements. `tm scheme show` lists each Status's requirements. A Scheme file is refused when a Status requires a field twice, one no layer defines, or one no write gives a value, such as `created` or `archived`, or when it removes a field a Status still requires.
