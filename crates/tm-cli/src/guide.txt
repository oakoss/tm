How to work with tm

This repo tracks its work as Issues in tm. Keep each Issue telling the
truth about the work, so the next session, human or Agent, can pick it up.

Find work
  tm prime                   who you write as, your Claims, the work in
                             progress and the ready queue
  tm ready                   the work that can start now, most urgent first
  tm show KEY                one Issue: its fields, Links, children by
                             Status and comments
  tm list parent:KEY         an Issue's children
  tm list is:blocked         the open Issues an open Issue blocks, each with
                             its blockers; blocked-by:KEY, what KEY blocks
  tm history KEY             what happened to an Issue, who did it, and
                             each write's batch for tm undo

Short-lists
  tm shortlist               the ordered lists of what to do next that you
                             work through, each member marked when it waits
  Change a list only when your human asks.

Start
  tm start KEY               when work starts, not when it ends: an Agent
                             claims the Issue, it moves to in_progress, and
                             it gains an Assignee if it has none
  tm next                    takes and starts the first Issue on your
                             Short-lists that can start now, or when no
                             Short-list names you, the most urgent ready
                             Issue on no list; --peek only shows it
  When your human names an Issue, start it; when they leave the choice to
  you, take the next.

Claims
  A Claim tells other Agents an Issue is taken. It lasts 2 hours unless
  .config/tm.toml sets claim_expiry, and every write from the session that
  took it renews it. Once it lapses, any other Agent may take it over.
  While it holds, other sessions cannot change the Issue's status or
  description; comment on it instead.
  tm heartbeat               renews this session's Claims through quiet
                             work, such as a long test run
  tm claims                  who holds which Issue, and for how long
  tm release KEY             gives a Claim up early
  tm claim KEY --for 30m     a shorter Claim; --no-expiry for none
  tm handoff KEY --to AGENT -
                             hands it to another Agent, with what is left
                             piped in as a note; tm prime shows it to that
                             Agent's sessions, and tm start KEY takes it
  tm setup claude            for a person: shows, asks, then adds hooks that
                             run tm prime at session start, heartbeat after
                             each tool use and release the session's Claims
                             when it ends
  tm setup codex             the same for Codex, in .codex/hooks.json
  Sessions of one Agent are told apart by the harness's session id, or
  TM_SESSION when set.

Keep it current
  The description holds the current plan. Change it with
    tm edit KEY --set description=-      (reads the text from stdin)
  Progress, what was learned and changes of plan go in comments, which
  keep a dated trail an edit would overwrite:
    tm comment KEY -                     (reads the text from stdin)
  Pipe long text in, from a file or a heredoc whose marker is quoted, so
  the shell leaves $, backticks and quotes in it alone:
    tm edit KEY --set description=- < plan.md
    tm comment KEY - <<'EOF'
    ...
    EOF
  Any --set FIELD=- on create, edit or move reads stdin, one field per
  command. Other fields, labels and the parent change with tm edit; the
  Status changes only with tm move.
  When you rewrite text you read earlier, pass the version tm show
  printed, --if-version N, so a change made since is refused, not lost.

A decision only your human can make
  When they are in the session, ask them there. When they are not, or it
  can wait:
    tm ask KEY "question"                parks the Issue on their answer and
                                         keeps your Claim for you; take
                                         other work with tm next
  Offer the likely replies with --option A --option B; they pick one by
  number or answer in their own words. What waits on your human shows in
  your tm prime; bring those questions to them and record each reply
  with tm answer KEY "reply". Once it is answered, tm start KEY in your
  next session resumes it. If you settle a question yourself first,
  withdraw it with tm withdraw KEY "why".

What the next session should know
  tm remember "fact"                     a durable fact about this Project,
                                         shown in every session's tm prime
  A memory is what a future session needs and cannot see in the code,
  such as how the tests must run or a trap in the build. Progress on an
  Issue goes in tm comment, and what AGENTS.md says needs no memory.
  Memories stay in this machine's tm, not in git, so a fact the whole
  repository needs belongs in AGENTS.md.
  Look in tm memories first; when one already says it, update it rather
  than write another, with tm remember --key KEY "fact", and when one is
  wrong, drop it with tm forget KEY.

New work found along the way
  tm create --type task --title TEXT --parent KEY
  tm link KEY blocks OTHER               to order it

Finish
  tm move KEY in_review                  when it is ready for review
  tm move KEY done                       when it has landed; this
                                         releases its Claim. An Agent
                                         cannot finish an Issue another
                                         session holds; --force does, once
                                         that session has stopped
  tm git scan                            after a merge and git fetch:
                                         moves each Issue a "Closes KEY"
                                         line names on the default branch
                                         to done; --dry-run shows what
                                         would move

Mistakes
  tm undo BATCH              undoes a command that printed
                             "undo this with: tm undo BATCH"
  tm undo                    a human undoes their own last command; run it
                             again to step further back

Agents
  Add --json to a command for one JSON document; an error carries a code,
  and a fix to run where there is one. A write's BATCH, for tm undo, is
  data.batch. tm export always writes JSONL.
