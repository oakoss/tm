# Claims apply by compare-and-set, and Links are keyed canonically

- Status: accepted
- Date: 2026-10-17
- Deciders: Jace Babin

## Context and Problem Statement

[ADR 0006](0006-operation-merge-ordering-and-versioning.md) says a pulled operation is always applied, that Claims are "decided by the authority, like Keys", and that Links merge as a set, per element. design.md adds that a take succeeds only on an unclaimed Issue, "never on 'already has that value'", that Links have deterministic keys, and that Links which would create a blocking cycle are refused. How must a take be checked and applied so that exactly one taker wins, locally and after sync, and how must a Link be keyed so that the same Link written from either end, on any Replica, is one element?

## Decision Drivers

- Exactly one of many concurrent takers wins, including takers that share an Agent name.
- A take that loses under sync stays in the log and is applied as lost, never refused or dropped.
- The outcome of replay is a function of log order alone, so every Replica rebuilds the same Claims.
- Per-element set merge through `field_versions` works for Links without a schema change.
- A blocking cycle empties the ready queue (design.md), and a cycle of Links or parents makes any walk of them loop. A merge can still produce one, so these checks follow design.md's rule for Workflow rules: checked when this Replica writes, never on replay.

## Decision Outcome

- **A Claim is its own operation kind, `claim`**, with an action of take, renew or release; it is never `set_field`, whose last-writer-wins merge ADR 0006 rules out for Claims.
- **A take is checked inside the `BEGIN IMMEDIATE` transaction that appends it.** Measured on macOS with 50 processes over 20 runs, that gave one winner every run; a check outside the transaction gave two or more winners in every run ([research](../research/workspaces/claims-and-links.md)).
- **The rule is strict.** An Issue already held is refused even when the holder has the taker's own Agent name; the refusal names the holder. With one shared name, a probe applying beads' idempotent rule told all 50 sessions they held the Issue.
- **A take records `prev`, the Claim it saw as current** (none when unclaimed), **and applies by compare-and-set**: in canonical order it wins only if the current Claim is still `prev`. Server order is then the authority with no server logic; unlike a Key, a Claim is decided by replay order, not written as a server effect.
- **A take that loses is kept in the log and recorded in `unapplied` as lost**, naming the Claim that won; the loss Notification and `tm doctor` read it from there, and `tm doctor` lists lost Claims apart from operations that do not fit.
- **The Claim's id is its token.** A release names it, so of several sessions sharing an Agent name only the one holding the token acts as the holder. Protected fields admit only the session that took the Claim, with no flag to name a token; `tm handoff` moves a Claim between sessions (amended 2026-10-25).
- **`tm move` into a Status whose category is done or cancelled releases the Issue's Claim**, lapsed or not, in the same batch, so the Agent needs no `tm release` for finished work. A move to any other Status, review included, keeps it, so the Agent holds the Issue through review. Whoever moves writes the release, which needs no token; the write is refused with `claim_changed` if the Claim changed after the move read it. An Agent's move is refused with `already_claimed` while another session, of any Agent, holds a live Claim on the Issue, unless it says `--force`, since an Agent finishing on a mistaken Key would end work in progress; the refusal names the holder and puts `--force` in its message, never its `fix`, so it is not run by rote. A human's move, a lapsed Claim and `tm git scan`, whose merged `Closes` line says the work is done, are not refused. An edit, a comment or a move that keeps the Claim leaves it in place, and `tm undo` of another session's take, which must name that batch, is not refused. Only `tm move` releases this way, and a take on a finished Issue is still allowed.
- **A live Claim protects its Issue's Status and description** (amended 2026-10-25). An Agent's write to either from any session but the holder's is refused with `already_claimed`, naming the holder and the field, unless it says `--force` (`tm edit`, `tm move`, `tm undo`), which again is in the message, never the `fix`. The check runs inside the write's transaction, as a take's does. A human's write goes through with a warning naming the holder, as does a forced one. A batch that takes or releases the Claim is judged by that Claim's rules instead, so the finishing move and `tm git scan` keep theirs, and an import records what happened elsewhere unrefused. Starting a child leaves a parent another session holds unstarted, with a warning, rather than refusing the child. Other fields, comments and Links stay open to anyone. design.md's recording of a forced write and its Notification to the holder wait for Notifications; the write's history names who wrote it.
- **A handoff is a fourth Claim action, `hand`, naming the Claim it replaces, the Agent it goes to and the note left for it** (amended 2026-10-26). The note travels in the operation, so every Replica shows it with the Claim, and is also written as a comment. It applies by compare-and-set, like a release: it stands only while that Claim, lapsed or not, is still the Issue's. It replaces it with a new Claim, whose id is the new token, held for the named Agent and for the human the old one was held for, in no session, marked handed, and lasting the old Claim's duration from the handoff. A take from that Agent, written for that human, stands over a live handed Claim, so its first session to `tm start` the Issue takes it and binds its session; inside the write transaction one of many such sessions wins, as with any take, and a Claim merely taken in no session is still refused, which is why the handed mark exists. A handed Claim is no session's until a take binds it, even for an Agent whose harness names no session, so nothing renews it or writes its protected fields until then. Neither a take nor a release could carry it: a take must name its writer, and one over a live Claim never stands. `tm handoff KEY --to AGENT "<note>"` writes the hand and the note as a comment in one batch; the holding session or the human it is held for hands off, and another session needs `--force`, named in the message only. `tm prime` lists a handed Claim, its giver and the note's first line to every session of the receiving Agent, and `tm next` passes it over, as it does any held Issue. Nobody renews a handed Claim, so one no session takes lapses. Undoing the handoff releases the handed Claim and retracts the note; the Claim it replaced is not taken back. The `claims` table gains a `handed` column, so the projection rebuilds.
- **A take carries its expiry duration, resolved when it is written.** With no `--for`, tm uses the Workspace's `claim_expiry` from `.config/tm.toml`: 2h by default, or `off` for none. `--no-expiry` takes a Claim that never lapses. Replay never reads config.
- **A renewal is a third Claim action, `renew`, naming the Claim's token and the duration it extends to.** It applies by compare-and-set, like a release: on replay it stands only if that Claim is still the Issue's, lapsed or not, and then sets the expiry to the renewal's recorded `utc_ms` plus the duration. A lapsed Claim no take has replaced therefore resumes on its holder's renewal; one taken over refuses it, recorded as lost. A Claim that never lapses cannot be renewed into one that does. Only the session that took a Claim may renew it, checked when written; replay holds a pulled renewal to the token alone, as it does a release.
- **A session's liveness renews its Claims.** Any write from a session renews each of its Claims due for it, whichever Issue the write touches, in the same batch; `tm heartbeat` renews them with no other write, and `tm heartbeat TM-n` renews that Issue's Claim before it is due. A Claim is due once a third of its duration has passed, so a busy session adds at most about three renewals per duration. Reads never renew, and a renewal is not activity on its Issue. Undoing a write leaves its renewal, which records that the session was active.
- **A release needs no token from the session holding the Claim or from the human it is held for**: tm looks the token up for them. Anyone else names it, and the token stays the only authority.
- **Expiry writes nothing.** The Claim stops holding, and `tm prime` shows it lapsed until the holding session's next write or heartbeat resumes it. Once another Agent has taken it over, a write by the old holder to that Issue warns it, as does any `tm heartbeat` from that session. design.md's Notification and comment on expiry are dropped.
- **A Claim lapses at its expiry, and a take over it names it as `prev`.** On replay, the take wins only if `prev` is still current and has lapsed by the take's recorded `utc_ms`, never by the replaying clock, so every Replica reaches the writer's verdict. A lapsed Claim no longer holds the Issue. `tm show` reports it as lapsed, and `tm prime` lists it to the session that took it unless the Issue is archived. Its row stays until a take replaces it or a release removes it, whether its holder's or a finishing move's. A Claim is never imported, as it says who works on an Issue now.
- **A take records the harness session that took it**, in its payload, so sessions sharing an Agent name tell their Claims apart: `tm prime` lists a session's own Claims apart from its other sessions', and a refused take or release names the holder's session. A take must name the session writing it. The session is `TM_SESSION`, else the harness's session id; a Claude Code sub-agent inherits its parent's id, so it is the parent's session unless `TM_SESSION` says otherwise. The session only records and displays; the token stays the only authority over a Claim.
- **A Link is keyed by `(type, source, target)` in canonical form.** A directional type is stored only outward ("B is blocked by A" is "A blocks B"); a symmetric type orders its two Issue ids by bytes. The type is part of the key. The operation is filed under the canonical source, with element `<type>/<target>`, so both ends and every Replica write the same `field_versions` row.
- **A Link type is stored as text** and checked against the built-in types only when written, as Scheme ids are ([ADR 0007](0007-the-projection-does-not-depend-on-the-scheme.md)).
- **A `blocks` Link or a parent that would close a cycle is refused when this Replica writes it; a cycle produced by merging is kept.** The check walks reachable Issues with the join order pinned (`reach CROSS JOIN links`): left to the planner, the walk over 10,000 Issues took 10.78 s instead of 0.013 s. The parent check is not measured. Anything that walks Links or parents must stop on a cycle.

### Consequences

- Good, because the take rule needs no new mechanism locally (the existing write transaction) and none at the server (its order decides).
- Good, because Links merge per element with no change to `field_versions`.
- Bad, because two sessions sharing an Agent name are told apart only by the Claim token, which the caller must keep.
- Bad, because a take made against a Claim that looked expired can beat a renewal it never saw; log order decides, and the renewal is recorded as lost.
- Bad, because a Link across Projects is filed in the source Project's chain only (see Open).

### Confirmation

Fifty processes taking one Issue get one success and refusals naming the winner, with distinct Agent names and with one shared name, on Linux and macOS. Two remote takes with no `prev`, acknowledged in order, rebuild with the first holding the Claim and the second recorded as lost. "A blocks B" written on A and "B is blocked by A" written on B rebuild as one Link, and a merged cycle survives a rebuild.
